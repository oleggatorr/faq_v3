# Обзор бизнес-логики

## Цель системы

Дать пользователю быстрый и простой способ отправить жалобу или предложение без регистрации и получить обратную связь через чат по `track_id`.

## Роли

- Пользователь:
  - создает тикет;
  - прикладывает файлы (опционально);
  - получает `track_id`;
  - ведет переписку по трек-номеру.
- Оператор:
  - видит тикеты в своей зоне доступа;
  - отвечает пользователю;
  - ведет внутренние заметки;
  - меняет статус/приоритет/категорию тикета.
- Администратор:
  - управляет операторами и доступами;
  - настраивает справочники (статусы, категории, отделы);
  - контролирует права и аудит действий.

## Ключевые сценарии

## 1) Создание обращения

1. Пользователь вводит данные и текст обращения.
2. Система создает тикет и первое сообщение.
3. Возвращается `track_id` для дальнейшего доступа к чату.

## 2) Переписка по обращению

1. Пользователь открывает чат по `track_id`.
2. Пишет новые сообщения и может прикладывать вложения.
3. Оператор отвечает в том же тикете.

## 3) Внутренняя работа оператора

1. Оператор может добавлять внутренние сообщения (`is_internal = true`).
2. Внутренние сообщения не видны пользователю.
3. Все важные изменения логируются как события тикета.

## Принципы доступа

- Внешний доступ пользователя к тикету идет через `track_id`.
- Доступ оператора ограничивается:
  - категориями из `category_access`;
  - действиями из `permissions`.

## Нефункциональные требования (базово)

- Устойчивость к угадыванию `track_id` (достаточная энтропия).
- Аудит ключевых действий операторов.
- Контроль размера и типа вложений.
