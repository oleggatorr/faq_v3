# Сервисы (Service Layer)

## Назначение раздела

Этот раздел описывает сервисный слой приложения: бизнес-операции, правила и orchestration между репозиториями, схемами и инфраструктурными компонентами.

Документ заполняется до реализации и уточняется по мере разработки.

## Принципы сервисного слоя

- Сервис содержит бизнес-логику, а не детали HTTP или ORM.
- Роутеры вызывают сервисы, а не работают с моделями напрямую.
- Сервисы принимают и возвращают понятные контрактные объекты (схемы/DTO).
- Ошибки домена формулируются на уровне сервиса и далее маппятся в API-ошибки.
- Транзакционные границы фиксируются на уровне конкретной сервисной операции.

### `AgentService`

- Управление операторами (CRUD, валидация бизнес-ограничений).
- Назначение прав и проверка допустимых комбинаций.

### `DepartmentService`

- Управление департаментами.
- Валидация связей с операторами и категориями.

### `TicketService`

- Создание тикета с первым сообщением (ключевая операция).
- Получение тикета по `track_id` (и/или по `id`) + опциональная загрузка сообщений/событий.
- Смена статуса тикета (в т.ч. закрытие/переоткрытие) и фиксация соответствующего события.
- Назначение ответственного (assign/unassign) и фиксация события.
- Изменение категории тикета (с учетом возможной синхронизации `department_id`).
- Объединение заявок (merge): связывание тикетов и фиксация события.
- Блокировка/разблокировка тикета (`is_locked`) и фиксация события.
- Базовая аннонимизация/маскирование данных тикета (если это соответствует выбранной бизнес-логике).

#### `create_ticket_with_first_message`

Операция создает тикет и сразу же добавляет первое сообщение пользователя.

Входные данные:
- `ticket_data`: схема `TicketCreate` (включает данные обращения: `track_id`, `customer_*`, `department_id`, `language_id`, `category_id`, `subject`, и т.д.).
- `first_message_body`: `str` (текст первого сообщения, т.е. будущего `MessageCreate.body`).
- Дополнительно (если потребуется для API-контракта): `first_message_subject`, флаги/атрибуты сообщения (по текущей схеме `MessageCreate` есть `is_internal`, `is_automatic`, `ip_address`, `agent_id`).

Выходные данные:
- `TicketRead` + `MessageRead` (т.к. сообщение создается отдельно после получения `ticket.id`).

Правила формирования preview:
- `ticket.preview_message` берется из `first_message_body`.
- Если длина `first_message_body` меньше или равна 200 символам, то `ticket.preview_message = first_message_body`.
- Если длина `first_message_body` больше 200 символов, то `ticket.preview_message = first_message_body[:200] + "..."` (многоточие для обозначения усечения).

Workflow (порядок действий):
1. Начать транзакцию (чтобы `ticket` и связанное первое `message` были согласованы).
2. Создать `Ticket` с данными из `ticket_data`.
   - `preview_message` на этом шаге можно оставить `NULL` (или вычислить сразу, но важно, что окончательное значение зависит от `first_message_body`).
3. Получить `ticket.id` (нужен для связи с `Message`).
4. Вычислить `preview_message` из `first_message_body[:200]` и сохранить `ticket.preview_message`.
5. Создать `Message` с `ticket_id = ticket.id` и `body = first_message_body`.
   - По умолчанию для пользовательского первого сообщения: `is_internal = false`, `is_automatic = false`, `agent_id = null`.
   - `customer_name`, `customer_email`, `ip_address` заполняются из `ticket_data` (если API не передает иные значения).
   - `subject` у первого сообщения всегда равен `ticket_data.subject` (тема тикета переносится в тему сообщения).
6. Обновить счетчик в тикете (минимально): `ticket.messages_count = 1` (или увеличить на 1, если в будущем появятся авто-сообщения при создании).
7. Завершить транзакцию.

Типовые доменные ошибки (черновик, уточним позже):
- `TrackIdAlreadyExists`: `ticket_data.track_id` уже используется.
- `ForeignKeyNotFound`: неверные `department_id`/`language_id`/`category_id`.
- `TicketCreationNotAllowed`: попытка создать тикет в недопустимом статусе (если появятся ограничения).
- `MessageCreationNotAllowed`: попытка создать первое сообщение при недопустимом состоянии тикета.

### `MessageService`

- Добавление сообщения в тикет (пользовательское или операторское, по флагам `is_internal`/`is_automatic`).
- Редактирование служебного сообщения (для заметок оператора, обычно `is_internal = true`).
- Удаление примечания/служебного сообщения (если политика удаления разрешает физическое удаление).
- Проверка прав отправителя и состояния тикета перед записью.
- Обновление счетчиков тикета (`ticket.messages_count`) и фиксация событий (например: `customer_replied`, `note_added`).

### `AttachmentService`

- Загрузка/сохранение файлов вложений и создание записи `Attachment` привязанной к `Message`.
- Валидация вложений (размер, mime/type, хэш/дедуп, ограничения по доступу).
- Подготовка полей `Attachment`:
  - `original_filename`, `stored_filename`, `file_path`, `file_size`, `mime_type`, `file_hash`
- Обновление счетчика тикета (`ticket.attachments_count`) после успешного добавления.
- Фиксация события `attachment_added`.

### `TicketEventService`

- Запись событий жизненного цикла тикета.
- Формирование ленты аудита для оператора.
- Политика аудита:
  - Любое изменение `tickets.status_id` должно порождать событие в `ticket_events`.
  - Все действия оператора, которые затрагивают пользовательские данные (см. примечание ниже) и `question_categories`, также должны порождать события аудита.
  - Для единообразия события создаются тем же сервисом, который выполняет доменное действие (либо через композицию с `TicketEventService`), в рамках той же транзакции.
- Единая точка для генерации `TicketEvent` по итогам действий других сервисов.
- Привязка `EventType` к операциям:
  - `created` — создание тикета+первого сообщения
  - `customer_replied` — ответ пользователя
  - `replied` — ответ оператора (если он отличается по типу от customer reply)
  - `status_changed` — смена статуса
  - `assigned`/`unassigned` — назначение/снятие ответственного
  - `category_changed` — изменение категории
  - `merged` — объединение заявок
  - `closed`/`reopened` — закрытие/переоткрытие
  - `locked`/`unlocked` — блокировка/разблокировка
  - `note_added` — добавление служебной заметки
  - `attachment_added` — добавление вложения

#### Статусы тикета (UI-плашки)

`TicketStatus` — справочник, отображаемый пользователям как “плашки” (например: “принято”, “на рассмотрении”, “ожидание ответа”, “закрыто” и т.п.).

В сервисе смены статуса правило такое:
- `TicketService.change_status(...)` всегда создает `TicketEvent` (тип `status_changed`, а также `closed`/`reopened`, если это закрытие/переоткрытие).

Точные пары `code <-> display name` заполняются данными из БД `ticket_statuses` (планируется seed-ом).

#### Примечание по “пользователям” для аудита

В текущей модели нет отдельной сущности “customer user” (пользовательские данные хранятся в `tickets`/`messages` как `customer_*` и `ip_address`).

Поэтому “все действия с пользователями” в документации трактуем так:
- изменения, затрагивающие customer-данные в контексте тикета (анонимизация/маскирование и т.п.) должны быть задокументированы как доменные операции `TicketService` и логироваться через `TicketEventService`;
- административные действия над `agents` (управление операторами) и действия из разряда “блокировать email/IP” требуют либо расширения `EventType`, либо отдельной аудит-таблицы (это TODO до согласования модели аудита).

### `OperatorPermissionsService`

- Проверка, имеет ли агент право выполнить действие над тикетом/категорией.
- Вход: `agent` (права), `ticket` (категория/департамент/статус), `action` (одно из перечисленных permissions).
- Выход: либо разрешение выполнения, либо доменная ошибка “нет прав”.
- Источник прав:
  - `Agent.category_access` (разделы/категории, которые оператор может обрабатывать)
  - `Agent.permissions` (перечень действий, которые оператор может выполнять)

#### Аудит действий по permissions

При реализации правил аудита делаем так:
- “чистые” права просмотра (просмотр заявок и т.п.) не порождают `TicketEvent` (если нет явного “кто смотрел” требования).
- Все права, которые изменяют состояние тикета/сообщений/категорий, порождают события через `TicketEventService`.
  - Примеры мутаций, которые должны логироваться: ответ на заявки (создание `Message`), удаление/объединение/назначение, смена статуса, смена категории, установка “решено” (через смену статуса или отдельное доменное правило), удаление примечания/служебного сообщения, редактирование служебных заметок.
- Права из списка, относящиеся к сущностям, которых пока нет в текущих моделях (`управление Базой знаний`, `шаблоны`, отдельные операции “блокировать email/IP адреса”, “управление пользователями” как отдельный домен), требуют:
  - согласовать модель аудита (какие `EventType` нужны);
  - при необходимости добавить новые таблицы/сущности.

## Что можно добавить в будущем (план расширений)

Ниже перечислены функции/операции из списка permissions, которые пока не поддержаны текущими моделями напрямую. На будущее они потребуют новых таблиц и расширения аудита (`TicketEvent` или отдельной аудит-таблицы).

### 1) Метки/labels для тикетов

- Назначение: “Установка/снятие меток на заявки”.
- Вероятные сущности: `labels`, `ticket_labels` (M2M).
- Аудит: отдельные события вида `labels_updated` (или аналогичные), чтобы фиксировать изменения.

### 2) Блокировки email и IP

- Назначение: “Может блокировать/разблокировать адреса Email” и “Может блокировать/разблокировать IP”.
- Вероятные сущности: `blocked_emails`, `blocked_ips` (или универсальная `blacklist` с типом).
- Аудит: новые `EventType` для “block/unblock”.

### 3) Анонимизация заявки

- Назначение: “Может анонимизировать заявку”.
- Вероятные реализации: маскирование/обнуление полей в `tickets`/`messages` + фиксируемое событие анонимизации.
- Аудит: новое событие `anonymized` (или набор событий: mask_customer_data).

### 4) База знаний

- Назначение: “Управление Базой знаний”.
- Вероятные сущности: `knowledge_articles` (и опционально `knowledge_categories`, `knowledge_attachments`).
- Аудит: события создания/редактирования/удаления статей.

### 5) Шаблоны ответов и шаблоны заявок

- Назначение: “Управление шаблонами ответов”, “Управление шаблонами заявок”.
- Вероятные сущности:
  - `response_templates` (для быстрого ответа оператором);
  - `ticket_templates` (для подготовки стартовых данных обращения);
  - при необходимости: `template_variables`/валидация параметров.
- Аудит: события публикации/изменения/использования (решим по бизнес-правилам).

### 6) Шаблоны email

- Назначение: “Редактировать шаблоны email” и отправка email-уведомлений.
- Вероятные сущности: `email_templates`.
- Аудит: изменения шаблонов (create/update/delete).

### 7) Настройки

- Назначение: “Управление настройками”.
- Вероятные реализации: `settings` (key-value) или отдельные таблицы по доменам.
- Аудит: `settings_changed` (или аналог).

### 8) Отчеты и экспорт

- Назначение: “Формирование собственных/всех отчётов”, “Экспорт заявок”.
- Вероятные сущности: `reports` (если нужно хранить результаты/параметры) + `exports` (лог экспортов).
- Аудит: “report_generated” / “export_created” (если требуется).

### 9) Управление пользователями (в разрезе операторов)

- В текущих моделях пользователь/оператор представлен как `agents`.
- Если “управление пользователями” включает отдельные бизнес-сущности (роли, группы, привязки) — могут понадобиться новые таблицы связей.
- Аудит: новые `EventType` для admin-операций над `agents` (сейчас в перечислении `EventType` их нет).

## Шаблон описания сервиса

Для каждого сервиса используем единый шаблон:

1. **Ответственность** - за что отвечает сервис.
2. **Операции** - публичные методы и их цель.
3. **Вход/выход** - какие схемы/DTO используются.
4. **Правила** - ключевые бизнес-ограничения.
5. **Ошибки** - доменные ошибки и условия их возникновения.
6. **Транзакции** - где нужны атомарные операции.
7. **Интеграции** - зависимости от других сервисов/репозиториев.
